## 온라인 (2시수)

### 강의: 근거를 찾는 것과 답을 만드는 것 - RAG의 다섯 단계

□ 문제부터 보기 - 문서가 있는데 왜 틀리는가

- 질문이 "제주도의 기후"라면 원문 전체를 넣을 수도 있다. 하지만 역사·행정·관광산업이 함께 들어가면 모델이 어느 문장을 사용할지 다시 골라야 한다. 7주차에서 본 **긴 입력 안의 근거 선택 문제**가 그대로 남는 상황
- RAG는 먼저 검색기로 관련 문단을 고른다. 문서 전체 대신 적은 문단을 전달하므로 입력을 줄일 수 있다. 대신 **검색기가 빠뜨린 문단은 생성 모델이 볼 수 없다는 새 병목** 발생
- 도서관에 비유하면 검색기는 책을 찾는 사서, 문맥 구성은 책에서 복사할 쪽을 고르는 과정, 생성 모델은 그 복사본으로 답안을 쓰는 사람. 다른 책을 가져오거나 필요한 쪽을 빼면 문장력이 좋아도 답의 근거 부족

<Image src={pipeline} width={1200} alt="공개 원문에서 문단 색인, 검색 후보, 재순위, 답변으로 이어지는 다섯 단계. 각 단계의 산출물과 출처 확인 위치를 표시한 개념도" />

- 그림은 왼쪽부터 읽되 **끝의 오답이 시작 단계의 탓이라고 바로 결론내리지 않는 것**이 핵심. 단계마다 실제 산출물 확인 필요

| 단계 | 입력 → 출력 | 확인할 질문 |
|---|---|---|
| 색인 | 원문 → 문단 ID와 벡터 | 정답 정보가 색인에 들어 있는가 |
| 검색 | 질문 → 후보 문단 k개 | 정답 문단이 후보 안에 있는가 |
| 재순위 | 후보 → 다시 정렬한 후보 | 직접 근거가 앞에 놓였는가 |
| 문맥 구성 | 상위 문단 → 길이 제한 내 문장 | 필요한 문장이 잘리지 않았는가 |
| 생성 | 근거와 질문 → 답변 | 답의 사실이 전달한 근거에 있는가 |

○ 원 논문과 수업 골격의 차이

- RAG 논문: 학습된 검색기와 생성 모델을 결합하는 방법 제시. 가중치에 저장된 패턴과 외부 문서 지식을 함께 사용하는 설계
- 수업 골격: TF-IDF로 검색, 단순 토큰 포함 기준으로 재순위, Qwen3-0.6B-Base로 짧은 생성. 검색기 학습과 공동 미세조정은 하지 않는 범위
- 따라서 이 실습은 논문 성능 재현이 아니다. **검색 한 단계를 바꿨을 때 후보·근거·답변이 어떻게 달라지는지 추적**하는 실험

### 단어를 숫자로 바꾸기 - TF-IDF를 손으로 계산

□ 먼저 빈도 행렬 만들기

- TF는 단어가 문서 안에 등장한 횟수. 그러나 모든 문서에 나오는 말까지 중요한 것으로 세면 질문의 차이를 구별하기 어려움
- IDF는 여러 문서에 퍼진 말의 가중치를 줄이고 드문 말에 더 큰 가중치를 주는 방법. **드물다와 참이다는 서로 다른 판단**임에 주의
- 아래 세 문자열은 계산용 예시. 제주 공개 원문의 인용이 아닌, 좌표를 세 개로 줄인 장난감 데이터

| 문서 | 계산용 문자열 | 제주 | 기후 | 관광 |
|---|---|---:|---:|---:|
| A | 제주 기후 기후 | 1 | 2 | 0 |
| B | 제주 관광 | 1 | 0 | 1 |
| C | 제주 | 1 | 0 | 0 |
| 질문 q | 제주 기후 | 1 | 1 | 0 |

- 문서 수 N = 3, 각 단어가 등장한 문서 수 df는 제주 3, 기후 1, 관광 1
- 같은 단어가 A에서 두 번 등장해도 기후의 df는 2가 아니라 1. TF는 횟수, df는 **문서 수**

○ 실습 라이브러리의 기본 IDF

```
idf(t) = ln((1 + N) / (1 + df(t))) + 1
제주: ln(4/4) + 1 = 1
기후: ln(4/2) + 1 = 1.6931
관광: ln(4/2) + 1 = 1.6931
```

- `1 +`는 기본 평활화 설정. 수업에서는 이 식으로 계산해 라이브러리의 설정과 숫자를 일치시키는 방식
- 단어 빈도에 IDF를 곱하면 A의 기후 좌표는 `2 x 1.6931 = 3.3863`. 이제 단순 빈도 대신 중요도 가중치 표현

| 벡터 | TF-IDF (제주, 기후, 관광) | L2 길이 | 정규화 후 |
|---|---|---:|---|
| A | (1, 3.3863, 0) | 3.5309 | (0.2832, 0.9591, 0) |
| B | (1, 0, 1.6931) | 1.9664 | (0.5085, 0, 0.8610) |
| C | (1, 0, 0) | 1 | (1, 0, 0) |
| q | (1, 1.6931, 0) | 1.9664 | (0.5085, 0.8610, 0) |

○ 코사인 유사도 - 길이보다 방향

```
cos(q, A) = (q · A) / (||q|| x ||A||)
정규화 후: 0.5085 x 0.2832 + 0.8610 x 0.9591 = 0.9698
cos(q, B) = 0.5085 x 0.5085 = 0.2586
cos(q, C) = 0.5085 x 1 = 0.5085
검색 순서: A → C → B
```

- "제주"만 있는 C보다 "제주 기후" 방향에 가까운 A가 먼저 나오는 결과. 관광 문서 B에도 제주가 있지만 기후 좌표가 없어 점수가 낮은 계산
- **점수 0.9698은 정답 확률 96.98%가 아니다.** 이 단어 좌표계에서 방향이 가깝다는 뜻. A에 잘못된 기후 설명을 써도 단어 구성이 같으면 높은 점수 가능
- 긴 문서를 무조건 먼저 뽑지 않도록 길이를 정규화했지만 문서의 사실성까지 검증한 것은 아닌 점

<Image src={vectorCalculation} width={1200} alt="계산용 A, B, C와 질문 q의 빈도 행렬, IDF 가중치, 정규화와 코사인 점수 0.9698, 0.5085, 0.2586을 연결한 계산 그림" />

- 그림 읽기: 왼쪽 빈도 행렬의 각 열에 가운데 IDF를 곱하고 정규화. 오른쪽 순위는 그 결과의 내적. **어느 단계에도 사실 확인 연산이 없다는 것**까지 읽는 연습

### 단어 검색과 문자 검색 - 후보가 생긴다는 것의 의미

□ 실제 색인의 크기

```
단어 색인: (58, 1801)
문자 색인: (58, 18572)
```

- 행 58은 문단 수, 열은 관찰된 특징 종류. 문자가 단어보다 작은 단위이지만 길이 2~4의 여러 연속 조합을 특징으로 만들기 때문에 열 수가 약 `18,572 / 1,801 = 10.31배`
- 이것을 메모리 10.31배로 읽으면 안 된다. 희소 행렬은 0이 아닌 값 중심으로 저장하므로 실제 메모리는 값의 개수와 저장 형식에도 의존

□ "한라산"과 "한라산의"의 차이

- 단어 분석기는 조사 제거 없이 정규식으로 단어를 분리. 질문 "한라산의 높이"의 단어 특징은 `한라산의`, `높이`
- 원문에는 `한라산`, `한라산을` 같은 표기가 있어도 정확히 같은 특징이 없으면 공유 좌표가 0. 현재 실습 질의의 단어 검색 후보가 빈 목록이 된 원인
- 문자 2-gram만 펼치면 "한라산의"에서 `한라`, `라산`, `산의` 생성. 문서의 "한라산"과 `한라`, `라산`을 공유할 수 있는 구조
- 하지만 `산의`가 겹쳐도 "높이"에 답한다는 뜻은 아니다. **문자 검색은 표기 차이를 일부 잇지만 질문 조건을 이해하는 모델이 아닌 방식**

- 고정 판·k = 5·같은 분할의 실행 결과. 같은 조건에서 검색 함수만 바뀌었을 때 관찰한 후보 변화
- 높이 질문: 0후보 → 5후보. **검색 결과가 생겼다**는 것은 사실. **높이 근거를 찾았다**는 것은 아직 판정하지 않은 주장
- 기후 질문: 정답을 뒷받침하는 D019가 문자 검색에서도 후보에 포함되지만 3위로 내려감. 후보 포함과 상위 문맥 선택을 따로 평가해야 하는 사례

□ 밀집 검색으로 바꾸면 해결되는가

- 밀집 검색은 학습된 벡터로 의미 유사도를 표현. DPR의 이중 인코더는 질문과 문단을 따로 인코딩해 문단 벡터를 미리 계산하는 구조
- 문자 겹침이 없어도 관련 의미를 찾을 가능성이 있지만 제주 지명, 한국어 조사, 높이·운영 시간 조건까지 잘 처리하는지는 별도 검증 필요
- 이번 노트북은 이중 인코더를 학습하지 않는다. 희소 검색에서 실패 원인을 읽는 것이 먼저이며 **검색 모델 이름을 바꾸는 것과 오류를 진단하는 것을 동일시하지 않는 순서**

### 재순위와 문맥 - 찾은 근거도 잃어버릴 수 있다

□ 후보 안에서만 다시 고르기

- 전체 문서를 자세히 비교하면 비용이 커질 수 있어 빠른 검색으로 후보를 좁힌 뒤 다시 관련성을 확인하는 구조
- 실습의 재순위는 단순 기준선: 질문의 단어가 문단 안에 부분 문자열로 포함된 비율. 학습된 cross-encoder가 아니며 문장을 읽어 조건을 판단하지 못하는 수준

```
overlap(q, d) = 문단 안에 포함된 질의 단어 수 / 질의 단어 수
정렬: overlap 내림차순 → 검색 점수 내림차순 → 문단 번호
```

- 질문에 단어 2개가 있고 한 개만 포함되면 1/2. 그러나 "높이"와 "한라산의"를 모두 놓친 후보들이라면 모두 0으로 동점, 결국 기존 검색 점수 순서를 유지
- 높이 질의의 문자 후보에서 D018을 먼저 고른 것은 재순위가 높이를 확인해서가 아니다. **후보들의 질의 토큰 포함 점수가 같아 검색 순서를 그대로 따른 결과**
- 운영 시간 질의에서는 문자 검색 2위 D035와 3위 D023이 재순위 후 자리 교체. 순서가 바뀐다는 사실만으로 관련성 개선이라고 말할 수 없는 점

○ 기후 질문의 실패를 한 단계씩 읽기

- 개선 실험의 방향: 질의에서 장소와 속성을 분리해 조건 일치 확인. 이번 TODO 범위에서는 자동 구현하지 않고 **어떤 지표와 근거로 개선을 검증할지** 제시하는 활동

□ 문맥 예산의 계산

- 검색 후보 수 k = 5와 생성 모델에 전달하는 문단 수는 다른 값. 현재 골격은 재순위 1위 문단의 선택 문장 한 개를 최대 600자로 제한
- 전체 프롬프트에도 768토큰 제한 적용. **600자는 600토큰이 아님**. 한국어 글자, 공백, 숫자가 모델 토큰으로 나뉘는 방식에 따라 길이 변화
- 설명용 토큰 예산: 전체 768, 지시문·질문 120이면 근거에 쓸 수 있는 예산은 648. 근거 3개가 각각 250토큰이면 750이라 102토큰 초과

### 검색 평가 - 무엇을 정답 근거로 셀까

□ 정답 라벨부터 확인

- 높이 질문에 "한라산"이 들어 있는 문단을 전부 정답으로 삼으면 D018 같은 동물 설명까지 정답 집합에 포함 가능
- 실습의 `proxy_hit`는 문자열 포함 문단의 후보 등장 여부. 높이 질의에서 False → True가 되어도 직접 근거를 찾았다는 뜻이 아님
- 지명 기반 예비 지표와 **사람이 확인한 질문별 정답 근거 집합**을 분리. gold_ids를 수동 판정 전에는 미판정으로 두는 이유
- 정답 근거가 없거나 아직 확인되지 않은 질문은 0점으로 뭉개지 않고 원문 범위·미판정 상태를 따로 기록

□ Hit@k, Recall@k, MRR 계산

- 아래는 계산 연습. 실제 제주 질문의 수동 정답 라벨을 꾸며 넣은 것이 아닌 예시
- 질문 Q1의 정답 근거는 A와 B 두 개. 검색 순서는 `[C, A, D]`, k = 3

```
Hit@3 = 1        (A가 있으므로 하나라도 찾음)
Recall@3 = 1/2  (A, B 중 A만 찾음)
RR = 1/2        (첫 정답 A가 2위)
```

- 질문 Q2에서 첫 정답 1위, Q3에서 정답 없음이라면 MRR = `(1/2 + 1 + 0) / 3 = 0.5`
- 세 지표가 동시에 보는 결과가 다른 이유: Hit은 존재, Recall은 근거 집합의 회수, MRR은 첫 근거의 앞쪽 배치
- Q1에 두 근거를 결합해야 답할 수 있다면 Hit이 1이어도 답변에 필요한 B가 없다. **검색 성공의 정의를 질문의 근거 요구에 맞춰야 하는 조건**

| 지표 | 높은 값의 의미 | 놓치는 것 |
|---|---|---|
| Hit@k | 적어도 하나의 정답 근거 발견 | 필요한 근거 전부인지 |
| Recall@k | 정답 근거 집합을 많이 회수 | 앞에 놓였는지, 답이 맞는지 |
| MRR | 첫 정답이 앞쪽에 배치 | 두 번째 필수 근거, 최종 생성 |
| 답변 정확성 | 질문의 답이 맞음 | 제공 근거로 뒷받침되는지 |
| 근거 충실성 | 답의 사실을 문맥이 지지 | 원문 자체의 최신성·사실성 |

○ 순위 전체를 비교하는 nDCG - 선택 심화

- 첫 정답만 보는 MRR은 뒤쪽 순서를 놓친다. 관련 문서가 여러 개이거나 관련성에 등급이 있으면 위치마다 이득을 할인하는 DCG 사용 가능
- 같은 Q1의 정답 집합 A·B를 유지하고, 다른 검색기가 `[A, C, B]`를 반환한 두 번째 예제를 비교. 앞의 `[C, A, D]`와 서로 다른 검색 순위
- 두 번째 예제의 관련성은 `[1, 0, 1]`. 이진 관련성에서 `gain = relevance`로 계산하며, 등급 관련성에서는 이득 정의를 먼저 고정할 필요

```
DCG@3 = sum(relevance_i / log2(i + 1))
관련성 [1, 0, 1]: DCG = 1/log2(2) + 1/log2(4) = 1.5
이상적 순서 [1, 1, 0]: IDCG = 1 + 1/log2(3) = 1.6309
nDCG@3 = 1.5 / 1.6309 = 0.9197
```

- 첫 번째 `[C, A, D]`의 관련성은 `[0, 1, 0]`. DCG = `1/log2(3) = 0.6309`, 같은 IDCG로 나누면 nDCG = `0.3869`. Recall은 1/2
- 두 번째 `[A, C, B]`는 두 정답을 모두 찾았으므로 Recall은 1. 그러나 B를 3위에 둔 비용을 nDCG가 반영해 0.9197. 첫 정답 순위만 보는 RR은 1
- 같은 정답 집합에 대한 두 검색 순위의 차이를 비교하는 계산이며 실제 제주 실측 아님. 원문 정답이 없는 경우는 평가 집계 규칙을 별도로 명시
- 이번 골격은 nDCG 자동 점수를 만들지 않는다. 미판정 gold_ids로 숫자를 내는 대신 손으로 지표 차이를 이해하는 활동

<Image src={rankingMetrics} width={1200} alt="정답 A·B가 같은 두 검색 순위 비교. 예제 1 C-A-D는 Recall 1/2, RR 1/2, nDCG 0.3869. 예제 2 A-C-B는 Recall 1, RR 1, nDCG 0.9197인 교육용 계산 그림" />

- 문자 검색의 후보에는 기후 문단 D019도 있었지만, 단순 재순위와 문장 선택으로 D011의 역사 문장을 전달. 후보 확보와 입력 근거 선택을 분리해서 확인해야 하는 이유
- 생성 답변이 기후에 관해 말한다는 사실만으로 근거를 잘 사용했다고 판정할 수 없음. 답변의 각 사실을 실제 입력 문장과 대조하는 순서
- 모델·토크나이저 revision: `da87bfb608c14b7cf20ba1ce41287e8de496c0cd`, 환경·seed·decoding 조건을 `execution_conditions`에 저장. 위 생성 예를 재검증할 때 동일 revision과 조건 대조
- 각 생성의 기록: 입력 제한 전 토큰 수·실제 입력 토큰 수·실제 출력 토큰 수·절단 여부·프롬프트와 실제 입력 ID hash·실제 입력 디코딩. `seconds`는 generate 구간만 측정
- 후보가 없어 생성하지 않은 경우 상태는 생성 생략, 소요 시간·토큰·hash는 null. 미측정을 0초 실행이나 0토큰 생성으로 표시하지 않음
- TODO를 바꾸지 않은 기본 실행은 기후 질문의 전후 근거·출력이 동일. 한 곳만 교체한 실행과 구분해 `generated_climate_before`·`generated_climate_after`에 저장
- 짧은 출력 제한은 CPU 비용을 줄이지만 답변 완결성을 희생. 입력 근거의 오류와 출력 길이 제한의 오류를 별도로 기록

## 대면 (1시수)

### 그래프 기반 검색 확장 - 두 번 연결했다고 답이 되는가

□ 문단 하나로 답하지 못하는 질문

- "장소 X가 속한 행정구역에서 제공하는 행사 Y는 무엇인가"라는 **가상의 질문 구조** 검토. 실제 제주 행사나 행정 관계를 꾸며 넣은 예시가 아닌 조건 설명
- 문서 A에는 장소 X의 소속 구역 Z, 문서 B에는 구역 Z와 행사 Y의 관계가 있다면 두 문서의 결합 필요
- 질문과 단어가 가까운 A만 찾으면 장소의 소속까지만 확인. B까지 찾아 같은 Z를 공유하는지 확인해야 답변의 조건을 이어 갈 수 있는 구조

```
장소 X --소속(문서 A, 기준 시점 t)--> 구역 Z
구역 Z --제공(문서 B, 기준 시점 t)--> 행사 Y
```

- 1홉은 X → Z, 2홉은 Z → Y. 그러나 **두 간선의 근거와 시점이 맞아야** "X가 속한 구역의 행사 Y"라는 답이 성립
- X와 Z가 같은 문장에 등장한 것만으로 소속 관계를 만들면 안 된다. 구역 이름이 같아도 동명이거나 기준 시점이 다르면 경로가 잘못 연결될 위험

<Image src={graph} width={1200} alt="문서 A, 개체 X, 출처가 있는 X와 Y의 관계, 문서 B, 확장 결과를 연결한 그래프 검색 개념도" />

- 그림 읽기: 문서 두 개를 단순히 모으는 것이 아니라 가운데 개체 판정과 관계 출처를 확인하는 과정. 이 그림도 실제 제주 관계 그래프 측정값이 아닌 모형

□ 확장의 비용과 제약

- 가상의 균일 분기수 b = 10, 시작 노드 1개. 중복·순환이 없다고 가정하면 1홉 10개, 2홉 최대 100개의 노드 검사. 시작점을 포함해 최대 111개 방문
- 2홉이라고 작은 작업이 아니다. 연결 수가 커지면 후보가 빠르게 늘어나므로 홉 수·관계 종류·날짜·개체 타입으로 탐색 범위 제한
- 실제 그래프에는 중복과 순환 존재. 방문한 노드 집합을 두지 않으면 같은 근거를 반복 수집하는 위험
- **문단 검색으로 해결할 조사 문제에 그래프를 붙이는 선택은 원인과 처방 불일치**. 표기 문제, 근거 누락, 관계 결합 문제를 먼저 구분

| 문제 | 그래프가 줄 수 있는 도움 | 그래프로 해결하지 못하는 것 |
|---|---|---|
| 여러 문서의 관계 결합 | 공유 개체와 관계를 따라 근거 연결 | 잘못된 개체 병합 |
| 문서 집합의 공통 주제 | 커뮤니티·요약으로 전체 구조 탐색 | 요약 과정의 누락·왜곡 |
| 조사 때문에 검색 후보 0개 | 직접적인 해결책으로 보기 어려움 | 토큰화·표현 문제 |
| 오늘의 운영 시간 없음 | 추가 근거 위치의 탐색 가능 | 원문에 없는 현재 사실 생성 |

□ GraphRAG 논문과 2홉 개념의 구분

- GraphRAG 논문은 개체 그래프와 커뮤니티 요약을 구성해 문서 집합 전체를 묻는 질문에 접근. 단순히 그래프에서 2홉 이웃을 가져오는 알고리즘과 다른 설계
- 앞의 X-Z-Y는 관계 결합을 이해하는 모형, 논문 재현이 아님. 커뮤니티 요약 구축·개체 추출·원문 갱신의 비용까지 검토하는 필요
- 큰 문서 집합의 주제를 묻는 질문과 특정 장소의 높이를 묻는 질문은 요구하는 근거의 형태가 다르므로 같은 확장법이 항상 유리하지 않은 점

**[실무]** 과제 3, **제공된 골격으로** 제주데이터허브·관광 빅데이터 플랫폼 공개 데이터 색인 구성 후 실패 유형과 원인 제시. 데이터 실물·접근·이용 조건을 먼저 확인하며, 다음 3단계 부분점수 구조 사용

- 3단계: 실패 유형·원인·개선안을 검증할 근거 제시

□ 데이터 실물 확인과 과제 범위

- [제주데이터허브](https://www.jejudatahub.net)와 [제주 관광 빅데이터 서비스 플랫폼](https://data.ijto.or.kr)의 공개 파일·필드·이용 조건은 교수자가 확인, 학생의 추가 수집 코드 작성 없음
- 노트북 7-1절에 완성된 CSV/JSON → `id, text, source` 어댑터와 단어·문자 검색 비교 코드 제공
- 준비 파일: `week09-public.csv` 또는 `week09-public.json`, 출처 설정 `week09-public-source.json`. 교수자가 확인해 배포한 원본·설정 파일을 런타임에 놓으면 코드 변경 없이 자동 대조
- 출처 설정 항목: 지정 포털의 HTTPS 자료 페이지, 확인한 이용 조건·수집 시각·파일 hash, 실제 공개 텍스트 컬럼, ID 컬럼 또는 null. 예시 컬럼을 실제 파일에서 확인한 필드로 간주하지 않는 원칙
- UTF-8 CSV 또는 행 객체 배열 JSON, 2MB 이내, 앞 50행 색인. 이름·연락처 필드를 선택하거나 도내 기업 자료를 연결하지 않기
- 원본·설정 파일이 없으면 **미수집**, hash·필드·이용 조건이 맞지 않으면 **미확인** 결과. 행 수와 검색·정답 판정의 미확인은 null로 보존
- 2026-10-11 재조회: 데이터허브 초기·이용 안내 경로의 HTTP 200은 실제 파일 확보 증거가 아님. 웹 조회에서는 방화벽 차단도 관찰
- 관광 포털 [방문 목적별 내국인 입도객 자료 페이지](https://data.ijto.or.kr/prog/dataPick/bigdata/sub02/view.do?regSn=20)의 CSV 형식 메타데이터는 검색으로 확인했으나 Python HTTPS 조회에서 인증서 검증 실패, 별도 curl 조회에서도 HTTP 403. 실제 파일·필드·이용 조건 미확인
- 현재 기본 실행의 포털 자료 상태는 미수집. 위키백과 기준선과 어댑터 준비 완료를 두 포털 자료 색인 과제 전체 완료로 보고하지 않는 구분
- 제공 어댑터의 검색 비교는 후보·근거 선택까지, 포털 자료의 생성·정답 판정은 미측정. 같은 생성 실험으로 확장하려면 확보한 자료의 질문·정답 근거를 먼저 확인
- 도내 기업 데이터 사용 금지. 데이터 원본을 커밋하지 않고 출처·수집 시각·해시·이용 조건 기록, 학번 폴더에 이름·연락처 미포함
- 정확한 배점과 제출 경로는 별도 과제 공지 기준

## 자주 하는 오해 Q&A

<details>
<summary>Q1. RAG를 붙이면 모델이 사실만 말하는가?</summary>

- 외부 문서를 전달하는 구조이지 사실 판정 장치가 아님. 실제 동물 문장을 받고 높이 `1000m`를 생성한 사례처럼 무관한 문맥에서도 유창한 답 생성 가능
- 검색 결과와 실제 문맥, 답의 사실을 각각 확인하는 필요

</details>

<details>
<summary>Q2. 문자 검색으로 후보가 늘었으니 단어 검색보다 우수한가?</summary>

- 높이 질문에서 0개에서 5개로 늘어난 것은 후보 수의 변화. D018의 동물 문장이 높이를 지지하지 않으므로 답변 근거 개선으로 볼 수 없는 결과
- 기후 질문은 직접 근거 D019 대신 역사 문장 D011이 선택. 질문별 실패를 읽어야 하는 이유

</details>

<details>
<summary>Q3. 검색 점수 0.97이면 정답일 확률 97%인가?</summary>

- 단어 좌표의 코사인 유사도이지 정답 확률이 아님. 계산용 A의 0.9698은 기후 특징이 질문과 비슷한 방향이라는 뜻
- 거짓 내용을 같은 단어로 쓰면 높은 점수가 나올 수 있고, 서로 다른 검색기 점수도 같은 확률 척도로 비교 불가

</details>

<details>
<summary>Q4. 재순위를 잘하면 모든 검색 실패를 고칠 수 있는가?</summary>

- 후보 안의 순서를 바꾸므로 후보 밖 정답 문서를 새로 찾지 못하는 구조. 인터랙티브의 k = 3에서는 재순위를 켜도 D4가 없음
- 후보가 있더라도 단순 토큰 포함 기준은 높이·시점 같은 조건을 충분히 확인하지 못함

</details>

<details>
<summary>Q5. 정답 문서가 후보 안에 있으니 생성 실패는 모델 탓인가?</summary>

- 최종 입력을 먼저 확인할 필요. 기후 질문의 D019는 후보에 있었지만 실제로 선택된 것은 D011. 모델은 기후 근거를 받지 못한 상태
- 모델에 전달된 근거가 충분할 때 비로소 근거 사용 실패를 분리하는 순서

</details>

<details>
<summary>Q6. 인용 ID가 붙은 답변은 근거가 있는가?</summary>

- ID는 문서 위치만 가리킴. `1000m`와 D018이 함께 출력되어도 D018의 동물 문장이 그 수치를 지지하지 않으면 근거 없는 인용
- 답의 각 사실과 실제 문장을 대조하는 판정 필요

</details>

<details>
<summary>Q7. Hit@5가 1이면 필요한 근거를 모두 찾은 것인가?</summary>

- 정답 두 개 중 하나만 찾아도 Hit은 1. 두 근거의 결합이 필요한 질문이면 Recall은 1/2이고 답할 정보가 부족할 수 있음
- 정답 근거 집합과 질문의 요구를 먼저 정의하는 필요

</details>

<details>
<summary>Q8. 그래프 2홉이면 연결된 사실을 답해도 되는가?</summary>

- 각 간선의 원문 근거, 개체 동일성, 시점이 일치해야 관계 결합 가능. 같은 문장에 등장한 개체를 임의로 연결하면 잘못된 경로 생성
- 그래프는 근거를 찾을 길을 제공할 수 있으나 누락된 현재 정보를 만들어 주지 않는 구조

</details>

## 이번 주 용어 정리

| 용어 | 한 줄 뜻 |
|---|---|
| RAG | 질문 관련 외부 근거를 검색해 생성 입력에 연결하는 구조 |
| chunk | 색인·검색 단위로 나눈 문서 조각 |
| 겹침 | 분할 경계의 정보 손실을 줄이기 위해 중복하는 부분 |
| TF / df | 문서 안 등장 횟수 / 해당 단어가 등장한 문서 수 |
| IDF | 여러 문서에 흔한 특징의 가중치를 줄이는 값 |
| L2 정규화 | 벡터를 길이 1로 맞추는 계산 |
| 코사인 유사도 | 벡터의 방향 유사도, 정답 확률과 구별 |
| 희소 검색 | 단어·문자 특징의 겹침을 사용하는 검색 |
| 문자 n-gram | 길이 n의 연속 문자 부분 문자열 |
| 밀집 검색 | 학습된 벡터로 의미 유사도를 표현하는 검색 |
| 이중 인코더 | 질문과 문단을 따로 인코딩하는 구조 |
| 재순위 | 이미 확보한 후보의 관련성을 다시 비교하는 단계 |
| 문맥 예산 | 생성 입력에 넣을 근거의 길이 제한 |
| grounding | 답의 사실을 실제 전달된 근거로 뒷받침하는 것 |
| Hit@k / Recall@k | 근거 하나라도 발견 / 정답 근거 집합의 회수 비율 |
| MRR | 첫 정답 근거 순위의 역수를 질문별 평균 |
| nDCG | 위치별 관련성 이득을 이상적 순서로 정규화한 값 |
