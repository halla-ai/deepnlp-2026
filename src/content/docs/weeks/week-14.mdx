## 온라인 (2시수)

### 강의: 배포 후 성능이 떨어지는 경로

□ 왜 최종 정확도만으로 실패를 설명하기 어려운가

- 개발 때의 "제주의 행정시는 몇 곳?"에 두 이름과 2곳을 반환하는 프로토타입
- 사용자가 "제주 두 도시의 총 개수는?"로 질문하면 같은 사실을 묻더라도 규칙의 키워드를 벗어나는 상황
- 모델을 고친 적이 없어도 응답 실패 발생. 프롬프트만 바꾸면 이름은 맞지만 count 필드가 사라지는 상황도 존재
- 한 점수로 묶으면 입력 대응 문제와 출력 계약 문제가 같은 "오답"으로 보이는 손실
- 해결 순서: 기준 실행 고정, 변화 항목 기록, 실패 수집, 같은 조건 재실행, 수신자 영향 검토

□ 입력 분포 이동(input distribution shift)

- 개발·평가 때 자주 보던 입력과 실제로 들어오는 입력의 분포가 달라지는 현상
- 질의의 어휘·길이·언어·목적·근거 요구 방식의 변화 가능
- 예제 F1: `행정시`라는 표현 대신 `두 도시의 총 개수`라는 작성 질의 사용
- 기준 코드와 프롬프트를 그대로 유지해도 키워드 조건을 통과하지 못해 `unsupported_input` 발생
- 이 한 예시는 입력 표현 변화의 실패 경로 시연. 지역 이용자의 실제 분포 이동을 추정하는 표본 아님
- 운영 확인: 실패 입력의 유형과 변화 시점 관찰. 실패 한 건을 전체 사용자 성능 저하로 일반화 금지

□ 프롬프트 갱신(prompt revision)

- 같은 질의와 같은 계산 규칙에도 출력 지시가 바뀌면 답 형식과 필드가 달라질 수 있는 구조
- 예제 F2: `prompt-v1`은 이름과 수 반환, `prompt-v2`는 이름만 반환
- 공개 이름은 남아 있으므로 사람이 두 곳이라고 추론할 수 있지만 자동 집계는 count 필드를 받지 못하는 상황
- 프롬프트 변경을 "문장만 수정"으로 보지 않고 출력 계약 변경 여부를 검토할 필요
- 실제 생성 모델에는 확률적 변화도 존재. 이번 규칙형 시연에는 난수·모델 호출 없음

□ 모델 갱신(model revision)

- 모델 가중치·토크나이저·추론 구현 등이 바뀌면 입력이 같아도 결과가 달라질 수 있는 경로
- 교육 예제에서는 학습을 하지 않고 `rule-v2`의 count 계산에 1을 더하는 오류를 삽입
- F3: 두 이름을 그대로 반환하지만 수는 3. 이름 포함 검사는 통과하고 count 검사는 실패
- 실제 모델 갱신의 효과를 재현한 실측이 아니라 변경 경로를 분리하기 위한 정책 모형
- 운영 확인: 모델 버전만 적지 않고 프롬프트·검색 자료·코드·실행 설정 버전도 함께 기록

□ 평가 지표의 노후화(stale metric)

- 시스템에서 필요한 판단이 달라졌는데 평가 기준은 예전 대상을 계속 측정하는 상태
- 예전 과업이 이름 안내였다면 이름 포함 검사는 일부 요구를 반영
- 지금 수신자가 자동 집계 프로그램이라면 count의 존재·형식·정확성도 계약에 포함
- 같은 출력에서 지표만 바꿔 판정이 달라지는 현상. 입력·프롬프트·모델 변화와 다른 관측 경로
- 지표가 나빠진 것인지 서비스 요구가 바뀐 것인지 구분하려면 평가 목적·버전 함께 기록

- 관찰 질문: F2와 F3가 이전 지표를 통과할 때, 어느 변경을 되돌려야 count가 복구되는지 예측

- 그림 해석: 실행 변경 세 종류와 측정 기준 변경 한 종류의 분리. 지표 노후화 자체를 새 모델 오류로 단정하지 않는 원칙

### 강의: 제공된 로깅·모니터링 코드 연결

□ 기록 없이 고치는 작업의 비용

- "한 번 이상했음"이라는 기억만 남으면 당시 질의·모델·자료·출력 계약을 알 수 없는 상태
- 최신 코드로 다시 실행하면 이전 실패가 사라져 원인 판단이 어려운 상황
- 단순히 로그를 늘리는 대신 재현에 필요한 식별자와 묶음을 먼저 정의
- 이번 실습: 완성된 `attach_monitor`와 두 로거 중 하나 연결. 새 logger·replayer를 학생이 작성하지 않는 방식

□ 기록 단위와 재현 단위의 차이

| 단위 | 이번 제공물 | 역할 | 한계 |
|---|---|---|---|
| 실행 기록 | `failures.jsonl` | ID, hash, 버전, 지연, 오류·판정 기록 | hash만으로 원문 복원 불가 |
| 공개 fixture registry | `bundle.json`의 fixtures | 작성 질의와 기대 count 연결 | 실제 개인 질의를 복사하는 방식으로 확장 금지 |
| 실행 묶음 | 같은 파일의 코드·config·retrieval | 이전 조건 고정 | 외부 모델 가중치 재현을 보장하지 않는 교육 모형 |
| 재현 대조 | 제공 replay 코드 출력 | 출력 hash·오류·판정 일치 확인 | 현재 CPU 지연의 동일 값 보장 불가 |

□ 최소 로그의 열

- `id`, `query_version`, `query_hash`, `output_hash`: 작성 질의와 결과 식별
- `model_version`, `prompt_version`, `config_id`, `config_hash`: 변경 조건 식별
- `retrieval_version`, `retrieval_hash`, `source_oldid`: 근거 자료 조건 식별
- `code_hash`, `bundle_hash`: 제공 코드와 전체 재현 묶음 대조
- `latency_ms`, `error`, `outcome`, `correct`: 실행 상태와 판정
- `metric_version`, `stale_metric_version`, `stale_pass`: 평가 대상 변화
- `source_verified`: 공개 사실 조회가 성공했는지 표시. 규칙 실행 성공과 별도

□ 한 곳 연결의 기본·대안

```python
# 기본: ID·hash·버전·판정 저장
run_with_monitor = attach_monitor(minimal_logger)
# 제공 대안: 이번 공개 작성 질의 열 추가
run_with_monitor = attach_monitor(public_fixture_logger)
```

- 노트북에는 기본 연결 한 줄만 TODO 표시
- 학생 활동: 기본 전체 실행 후 `minimal_logger`를 `public_fixture_logger`로 교체하고 전체 재실행
- 알고리즘 추가가 아닌 제공 코드 연결 정책 선택
- 두 방식에서 같은 실패 3건과 replay 결과 유지. 대안에서만 `public_authored_query` 열 추가
- 대안은 이번 공개 작성 질의만 허용. 실제 개인 원문·토큰·이름·연락처를 로그에 넣는 정책 아님

□ hash가 개인정보 보호를 보장하지 않는 이유

- 후보가 적은 질의는 후보별 hash를 계산해 원문을 추정하는 공격 가능
- 식별자 자체도 다른 로그와 결합되면 관계 정보가 될 수 있는 구조
- 원문 최소화는 수집량을 줄이는 선택, 법적 익명화나 보안 보장과 별개
- 운영에서는 목적·접근 권한·보존 범위·삭제 조건 검토 필요
- 이번 공개 fixture 파일은 공개 작성 질문의 재현용. 개인 사용자 registry 구축 요구 없음

- 관찰 질문: 로그 파일만 있고 `bundle.json`이 없다면 질의 hash를 보고 그대로 실행할 수 있는지 예측

<Image src={replay} width={1200} alt="최소 로그의 ID와 hash를 별도 공개 fixture, 코드와 설정 묶음에 연결하고 재실행 출력과 대조하는 구조" />

- 그림 해석: 로그의 원문 축소와 공개 fixture의 확보를 함께 설계. hash만 저장했다고 재현이 저절로 가능해지는 것은 아님

□ 지연은 시각이 아닌 경과 시간

- `perf_counter()`는 짧은 실행 시간 측정에 사용하는 고해상도 시계
- 계산: `latency_ms = (끝 값 - 시작 값) × 1000`
- 작은 대입 예: 시작 100.000초, 끝 100.003초라면 `(0.003) × 1000 = 3ms`. 설명용 수치, 이번 노트북 실측 아님
- 노트북 지연은 현재 실행에서 각 행에 측정. 하드웨어·프로세스 부하에 따라 달라질 수 있는 값
- 버전·출력 hash는 일치 대상, 경과 시간의 byte 일치는 재현 조건에서 제외
- 측정 누락을 0ms로 채우지 않는 원칙. 네트워크 서비스의 지연으로 일반화 금지

### 강의: 실패 3건과 노후 지표의 차이

□ 출력 결과부터 보는 작은 실험

| ID | 변경 조건 | 실제 제공 규칙 출력 | count 기준 | 이전 이름 포함 기준 |
|---|---|---|---|---|
| 기준 | 기본 질의, rule-v1·prompt-v1 | 제주시, 서귀포시, 2곳 | 통과 | 통과 |
| F1 | 표현 이동, 기본 버전 유지 | 판단 보류 | 실패: 값 없음 | 실패 |
| F2 | 기본 질의, prompt-v2 | 제주시, 서귀포시 | 실패: 값 없음 | 통과 |
| F3 | 기본 질의, rule-v2 | 제주시, 서귀포시, 3곳 | 실패: 값 3 | 통과 |

- 표는 노트북의 결정적 작성 규칙을 설명하는 기대 출력. 노트북 실행 결과와 대조할 대상
- 모델 생성 결과·기업 장애 통계·자연 발생 실패 수집이라고 표기하지 않는 원칙
- 실패 케이스 셋만 보면 새 지표 통과 `0/3 = 0%`, 이전 지표 통과 `2/3 ≈ 66.7%`
- 분모 3은 의도적으로 실패를 넣은 교육 집합. 운영 트래픽의 정확도 추정 분모 아님
- 기준 실행은 비교용이며 실패 기록 파일에는 F1·F2·F3 세 행만 저장

□ 무엇이 원인이고 무엇이 관측인가

- F1: 입력에 없는 키워드로 미응답. 모델 변경으로 판정할 근거 없음
- F2: count 누락이지만 예외 없음. `error=None`을 성공으로 간주하면 놓치는 출력 계약 실패
- F3: 잘못된 수치지만 예외 없음. 예외 감시와 의미 품질 감시를 따로 둘 이유
- 이전 지표의 2/3 통과: 두 이름 존재만 측정하므로 새 요구의 누락·모순을 놓치는 관측
- 코드 예외, 응답 유무, 필드 계약, 사실 일치의 별도 열 필요

□ 정답 라벨이 없는 실제 입력

- 교육 fixture에는 기대 count 2가 있으므로 exact-count 비교 가능
- 실제 운영에서는 입력이 들어왔어도 정답 검토가 아직 없을 수 있는 상태
- `correct=None`, `outcome=unknown`으로 표시. 실패도 성공도 확정하지 않는 원칙
- 정확도 분모: 라벨 확인된 건수. 함께 보고할 라벨 커버리지: 확인된 건수 / 전체 기록 수
- 예: 5건 중 라벨 3건, 그중 통과 2건이면 정확도 `2/3`, 라벨 커버리지 `3/5`. 설명용 계산, 이번 실패 표의 실측 아님
- 라벨 없는 2건을 오답으로 채우면 `2/5`, 제외 사실을 숨기면 커버리지 공백. 둘 모두 오해를 만드는 방식

- 관찰 질문: 이전 지표가 66.7%이면 수신 프로그램에 count를 보내도 되는지 판단

- 그림 해석: 예전 측정 대상이 새 출력 계약을 덮지 못하는 상황. 통과 비율 상승만으로 현재 서비스 요구 충족 선언 불가

□ 재현 성공은 품질 성공이 아님

- 제공 replay는 저장된 코드·질의·검색 자료·config hash와 묶음 hash를 먼저 대조
- 같은 조건으로 F1·F2·F3를 실행한 뒤 출력 hash·오류·판정을 검증
- 세 실패가 그대로 돌아오는 것이 replay 통과
- 품질 관점에서는 여전히 세 실패. 재현을 확보했으므로 변경 전후 비교가 가능해진 상태
- 바뀐 코드를 이전 hash로 속이거나, 최신 자료로 과거 결과를 덮어쓰지 않는 원칙
- 현재 규칙 모형은 결정적. 실제 생성 시스템은 seed·추론 설정·가중치·실행 환경을 추가로 고정해도 완전 일치가 어려울 수 있는 한계

| 모니터링 | 기록에서 상태·품질 관찰 | 정답 없는 정확도 계산 |

| hash | 동일 자료 대조용 요약값 | 복원·익명화 보장 |
| 라벨 커버리지 | 정답 확인 건수 / 전체 건수 | 확인된 건의 정확도 |
| 멀티롤 | 개발·운영·소통을 한 사람이 겸하는 조건 | 실제 담당자를 임의 지정 |
