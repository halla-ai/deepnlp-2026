## 온라인 (2시수)

### 강의: 텐서 연산과 자동미분, 사전학습 모델 로딩

□ 텐서 - 숫자를 담는 상자

- 텐서(tensor)는 겁낼 것 없이 **숫자를 담는 상자**다. 상자의 모양에 따라 이름만 달라진다
- 스칼라: 숫자 하나 (예: 오늘 기온 27)
- 벡터: 숫자를 일렬로 놓은 것 (예: 일주일치 기온 7개)
- 행렬: 숫자를 바둑판처럼 놓은 것 (예: 반 학생 30명의 국어·영어·수학 점수, 30줄 x 3칸)
- 그 이상: 행렬을 여러 장 쌓은 것 (예: 우리 학년 5개 반 전부의 점수)
- NLP에서 텐서가 하는 일: 토큰 번호를 숫자 묶음으로 바꿔 담고(임베딩), 행렬 곱셈으로 표현을 섞고, 마지막에 확률로 낸다. 모델의 가중치(모델이 기억하는 값)도 전부 텐서다. "모델이 크다"는 말은 곧 "텐서가 크다"는 말이다
- GPU가 잘하는 일이 바로 이 텐서 연산을 **수천 개씩 동시에** 하는 것이다. 같은 계산을 엄청나게 많이, 동시에 - 이것이 AI에 GPU가 필요한 이유다

<img src={tensorShapes.src} alt="숫자 하나짜리 스칼라, 기온 7개를 일렬로 놓은 벡터, 30명의 세 과목 점수를 표로 놓은 행렬, 반 5개의 표를 겹쳐 쌓은 3차원 텐서를 모양(shape)과 함께 보여주는 그림" style="max-width: 100%; border-radius: 8px; margin: 1rem 0;" />

○ shape - 상자의 크기표

- 텐서마다 **shape**라는 크기표가 붙는다. 괄호 안의 숫자 개수가 차원 수, 각 숫자가 그 방향의 칸 수다
- 스칼라는 `()`, 일주일 기온은 `(7,)`, 30명의 세 과목 점수는 `(30, 3)`, 5개 반 전체는 `(5, 30, 3)`이다. 읽는 순서는 "반 5개 → 학생 30명 → 과목 3개"처럼 **바깥 상자부터 안쪽으로**다
- 칸의 총 개수는 shape의 숫자를 모두 곱한 값이다. `(5, 30, 3)`이면 5 x 30 x 3 = 450칸이다. 1주차의 메모리 계산(칸 수 x 4바이트)과 같은 원리다
- NLP에서 자주 보는 모양은 `(배치, 토큰 수, 숫자 묶음 크기)`다. 문장 8개를 한 번에 넣고, 문장마다 토큰 128개, 토큰마다 숫자 768개로 표현하면 `(8, 128, 768)`이다

○ 행렬 곱셈 손으로 한 번

- 모델 안에서 가장 많이 일어나는 계산이 행렬 곱셈이다. 2 x 2로 한 번만 손으로 해 보면 겁낼 이유가 사라진다
- `[[1, 2], [3, 4]]`와 `[[5, 6], [7, 8]]`을 곱한다. 규칙은 "**왼쪽 행렬의 가로줄**과 **오른쪽 행렬의 세로줄**을 짝지어 곱해서 더한다"이다
- 왼쪽 첫째 줄 [1, 2]와 오른쪽 첫째 세로줄 [5, 7]: 1 x 5 + 2 x 7 = **19**
- 왼쪽 첫째 줄 [1, 2]와 오른쪽 둘째 세로줄 [6, 8]: 1 x 6 + 2 x 8 = **22**
- 왼쪽 둘째 줄 [3, 4]와 [5, 7]: 3 x 5 + 4 x 7 = **43**, [3, 4]와 [6, 8]: 3 x 6 + 4 x 8 = **50**
- 결과는 `[[19, 22], [43, 50]]`이다. 1주차 어텐션의 "내적"이 바로 이 "짝지어 곱해 더하기" 한 번이다

○ shape가 안 맞으면 생기는 일

- 행렬 곱셈에는 조건이 하나 있다. **왼쪽의 가로 칸 수와 오른쪽의 세로 칸 수가 같아야** 짝을 지을 수 있다. `(2, 3)` 곱하기 `(3, 2)`는 되지만 `(2, 3)` 곱하기 `(2, 3)`은 안 된다
- 조건이 깨지면 코드는 멈추고 오류를 낸다. 실습에서 가장 흔한 오류가 이것이다

```python
import torch
a = torch.ones(2, 3)
b = torch.ones(2, 3)
a @ b        # 오류
a @ b.T      # b를 뒤집어 (3, 2)로 만들면 성공, 결과 shape는 (2, 2)
```

- 첫 번째 곱셈을 실행하면 오류 메시지의 마지막 줄에 `mat1 and mat2 shapes cannot be multiplied (2x3 and 2x3)`가 찍힌다. "두 행렬의 모양이 2x3과 2x3이라 곱할 수 없다"는 뜻이다. 괄호 안 숫자만 읽으면 **무엇이 안 맞는지** 바로 보인다
- `.T`는 행렬의 가로와 세로를 뒤집는다. `(2, 3)`이 `(3, 2)`가 되어 짝이 맞고, 결과는 `(2, 2)`다

□ 자동미분 - 어디서 틀렸는지 거꾸로 따라가기

- 모델을 가르치려면 "얼마나, 어느 쪽으로 틀렸는지"를 알아야 한다. 그 답이 **그래디언트(기울기)** 다
- 비유: 시험에서 감점됐을 때 "어느 문제의 어느 풀이 단계에서 점수가 깎였나"를 거꾸로 추적하는 것과 같다. 총점(손실)만 봐서는 고칠 곳을 모른다. 단계별 감점(각 가중치의 그래디언트)을 알아야 고친다
- 원리는 하나다. `requires_grad=True`로 표시한 텐서에 연산을 걸면, 프레임워크가 **연산 기록(계산 그래프)** 을 메모해 둔다. `loss.backward()`를 부르면 그 메모를 거슬러 올라가며 각 텐서의 감점표(그래디언트)가 채워진다
- 실습 노트북 1-1의 실측값으로 확인한다. `loss = (w*x + b - 10)^2`이고 `w=2, x=3, b=1`일 때:

| 항목 | 값 | 뜻 |
|---|---|---|
| loss | 9.0000 | (2 x 3 + 1 - 10)^2 = (-3)^2 |
| d(loss)/dw | -18.0000 | w를 조금 키우면 loss가 그 18배만큼 줄어드는 방향 |
| d(loss)/dx | -12.0000 | x에 대한 기울기 |
| d(loss)/db | -6.0000 | b에 대한 기울기 |

- 손으로도 확인해 본다. `w*x+b = 7`이고 `loss = (7-10)^2 = 9`. 미분의 연쇄법칙(겉미분 x 속미분)으로 `d(loss)/dw = 2*(7-10)*x = -18`. 코드 출력과 정확히 일치한다. **자동미분은 마법이 아니라 연쇄법칙을 기계가 대신 적용해 주는 것**이다

<img src={autogradGraph.src} alt="w, x, b가 w*x+b를 거쳐 loss로 흐르는 순전파와, 그래디언트가 거꾸로 흐르는 역전파를 실제 숫자와 함께 보여주는 계산 그래프" style="max-width: 100%; border-radius: 8px; margin: 1rem 0;" />

□ 기울기로 한 걸음씩 - 경사하강법을 손으로

- 그래디언트를 구했으면 이제 고친다. 짙은 안개 속 언덕에서 골짜기 바닥으로 내려가는 사람을 떠올리자. 멀리는 안 보이지만 **발밑의 경사**는 느낄 수 있다. 내리막 쪽으로 한 걸음 옮기고, 다시 경사를 느끼고, 또 한 걸음. 이것이 **경사하강법**(gradient descent)이다
- 가장 단순한 예로 따라가 본다. 손실이 `loss = (w - 3)^2`인 문제다. 정답은 w = 3이고 그때 손실은 0이다. 시작은 w = 0, 한 걸음 크기인 학습률은 lr = 0.1이다
- 기울기는 `d(loss)/dw = 2 x (w - 3)`이다. 갱신 규칙은 `새 w = w - lr x 기울기`다

| 걸음 | w | loss = (w-3)^2 | 기울기 2(w-3) | 다음 w 계산 |
|---|---|---|---|---|
| 0 | 0 | 9 | -6 | 0 - 0.1 x (-6) = 0.6 |
| 1 | 0.6 | 5.76 | -4.8 | 0.6 - 0.1 x (-4.8) = 1.08 |
| 2 | 1.08 | 3.6864 | -3.84 | 1.08 - 0.1 x (-3.84) = 1.464 |
| 3 | 1.464 | 2.359296 | -3.072 | (다음 걸음으로) |

- 표를 읽는 요령이 두 가지다. 첫째, 기울기가 **음수**면 w를 **키우는** 쪽이 내리막이다. 갱신식의 빼기가 음수를 만나 더하기가 된다. 둘째, 바닥에 가까워질수록 기울기가 작아져서 **걸음도 저절로 작아진다** (-6 → -4.8 → -3.84)

<img src={gdSteps.src} alt="loss = (w-3)^2 포물선 위에서 w가 0, 0.6, 1.08, 1.464로 이동하며 손실이 9, 5.76, 3.686, 2.359로 줄어드는 세 걸음을 화살표로 보여주는 그래프" style="max-width: 100%; border-radius: 8px; margin: 1rem 0;" />

- 실제 모델에서는 "딱 맞는 크기"를 미리 알 수 없다. 그래서 작게 시작해 손실 곡선을 보며 조정한다. **손실이 줄지 않고 오히려 커지면 학습률부터 의심**하는 습관을 들인다

□ 학습 루프 - 네 단계의 반복

- 모델을 가르치는 일은 다음 네 단계를 **수백, 수천 번 반복**하는 것이다
- 순전파: 입력을 넣어 예측을 계산한다 (문제를 푼다)
- 손실: 예측과 정답의 차이를 숫자 하나로 만든다 (채점한다)
- 역전파: `loss.backward()`로 각 가중치의 그래디언트를 구한다 (감점 원인을 추적한다)
- 갱신: `w -= lr * w.grad`로 그래디언트 반대 방향으로 한 걸음 이동한다 (틀린 쪽의 반대로 고친다). `lr`(학습률)은 한 걸음의 크기다

- 실습 노트북 1-2의 실측값. 정답이 `y = 3x + 1`인 데이터를 맞추는 선형 모델이다. 처음에는 w=0.5, b=0으로 엉터리지만, 반복할수록 정답에 다가간다:

| step | loss |
|---|---|
| 0 | 60.375000 |
| 40 | 0.002392 |
| 80 | 0.001861 |
| 120 | 0.001464 |
| 160 | 0.001152 |

- 200 step 후 `w = 3.025, b = 0.926`. 정답(w=3, b=1)에 거의 도달했다. **손실이 낮아지는 것 = 모델이 데이터에 맞춰지고 있다는 증거**다. 이 그림 한 장이 "학습된다"는 말의 전부다
- 손실 함수(채점 기준)를 바꾸면 같은 데이터에서도 감소 곡선이 달라진다. 평균제곱오차(MSE)는 큰 오차를 세게 혼내고(제곱이라), 평균절대오차(MAE)는 오차 크기만큼만 혼낸다. 이것이 이번 주 노트북의 TODO 한 지점이다

○ MSE와 MAE를 숫자 3개로 비교

- 예측이 [2, 5, 9], 정답이 [3, 5, 5]라고 하자. 오차(예측 - 정답)는 [-1, 0, 4]다
- MSE: 오차를 제곱해 평균. (1 + 0 + 16) / 3 = **5.667**
- MAE: 오차의 절댓값을 평균. (1 + 0 + 4) / 3 = **1.667**
- MSE에서는 오차 4 하나가 합계 17 중 16을 차지한다. **크게 틀린 하나가 점수를 좌우**한다. MAE에서는 5 중 4다. 이상하게 튀는 데이터(이상치)가 섞여 있으면 MSE는 그쪽에 끌려가고, MAE는 덜 흔들린다

○ 채점 기준만 바꿔 학습해 보면

- 정답이 y = 3x + 1인 입력 20개로, 시작점(w=0.5, b=0)과 학습률(0.05)을 같게 두고 손실 함수만 바꿔 200 step 돌렸다 (강의용 스크립트 실행값. 노트북과 데이터가 달라 숫자는 다르다)

| 손실 함수 | step 0 | step 50 | step 200 | step 200의 w, b |
|---|---|---|---|---|
| MSE | 10.2105 | 0.0000 | 0.0000 | 3.000, 1.000 |
| MAE | 2.7263 | 0.2425 | 0.0150 | 3.005, 0.985 |

<img src={mseVsMae.src} alt="같은 문제를 MSE와 MAE로 학습한 손실 곡선 비교. MSE는 50 step 안에 거의 0이 되고, MAE는 200 step에도 0.0150에 머무름" style="max-width: 100%; border-radius: 8px; margin: 1rem 0;" />

- 두 손실은 **점수의 단위가 달라서** 숫자 크기를 직접 비교하면 안 된다. 비교할 것은 곡선의 모양과 최종 w, b다
- 이 데이터에는 이상치가 없어서 MSE가 더 빨리, 더 정확히 도착했다. MAE는 오차 하나당 기울기가 크기와 상관없이 +1 또는 -1이라, 바닥 근처에서도 걸음이 줄지 않고 **왔다 갔다** 한다. 실제로 한 step 뒤에는 b가 0.985에서 1.035로 넘어가 손실이 0.035로 다시 커진다. 노트북 TODO에서 이 차이를 직접 보게 된다

○ 배치, 에폭, step - 반복을 세는 세 단위

- 데이터가 많으면 한 번에 다 넣지 않고 조금씩 나눠 넣는다. 반 전체 쪽지시험을 떠올리자
- **배치**(batch): 한 번에 채점하는 답안지 묶음. 32장씩 채점하면 배치 크기 32
- **step**: 배치 하나를 채점하고 고치는 한 번. 학습 루프 네 단계가 한 바퀴 도는 단위다
- **에폭**(epoch): 모든 답안지를 한 번씩 다 본 것
- 계산 예: 답안지(데이터) 2,400장을 배치 16으로 나누면 한 에폭은 2,400 / 16 = **150 step**이다. 3주차 실습이 NSMC 2,400건으로 에폭 1회를 도는데, 이때 몇 step인지는 배치 크기에 달려 있다

□ 사전학습 모델 로딩 - 경력직 데려오기

- 우리는 가중치를 처음부터 만들지 않는다. 이미 엄청난 분량의 글을 읽고 학습된 모델을 **그대로 가져와** 그 위에서 작업한다. 새 직원을 뽑아 1부터 가르치는 대신, 경력직을 데려오는 것과 같다
- 로딩은 두 조각이다. **토크나이저**(글자를 잘라 숫자로 바꾸는 번역기)와 **모델**(그 숫자를 받아 계산하는 본체)

<img src={modelLoading.src} alt="문장 혼저 옵서예.가 토크나이저를 거쳐 토큰 번호 목록이 되고, 체크포인트에서 불러온 가중치를 가진 모델 본체를 지나, 새로 초기화된 분류 헤드에서 확률이 되는 흐름도" style="max-width: 100%; border-radius: 8px; margin: 1rem 0;" />

- 문장 하나가 판정되기까지를 순서대로 따라가 본다
- 1단계, 문장: "혼저 옵서예." 같은 사람의 글이 들어온다
- 2단계, 토크나이저: 글을 조각내고 조각마다 사전에 적힌 **번호**를 붙인다. 1주차에서 말한 토큰이 여기서 만들어진다
- 3단계, 토큰 번호 목록: 번호들이 텐서로 묶인다. 문장이 여러 개면 shape는 `(문장 수, 토큰 수)`다
- 4단계, 모델 본체: 체크포인트(미리 학습해 저장해 둔 가중치 파일)에서 불러온 값으로 계산해 문장의 의미를 숫자 묶음으로 만든다
- 5단계, 분류 헤드: 그 숫자 묶음을 "긍정/부정" 같은 판정 점수로 바꾸고, softmax로 확률을 낸다
- 토크나이저와 모델은 **반드시 짝을 맞춰** 불러온다. 다른 모델의 토크나이저를 쓰면 번호표가 달라서, 모델은 엉뚱한 단어로 읽는다. 오류 없이 돌아가지만 결과가 엉망이 되는, 가장 찾기 어려운 실수다
- 실습에서 쓰는 한국어 모델(KoELECTRA base)의 전체 파라미터 수는 **112,922,882개(약 1.1억)** 다. 이 숫자를 기억해 둔다. 3주차에서 LoRA가 학습 파라미터를 얼마나 줄이는지 이 수가 기준선이 된다
- 분류 과제용으로 불러오면 분류 헤드(마지막 판정 부품) 가중치가 체크포인트에 없어서 **새로 초기화**된다는 경고가 뜬다. 고장이 아니라 "이 부품은 직접 데이터로 새로 길들여야 한다"는 안내다

- 튜토리얼 코드(실습 노트북)를 한국어 데이터로 바꿔 실행하고, 막힌 지점을 튜터에게 질의한다
- 질의할 때는 오류 메시지의 **마지막 줄**을 함께 제시한다. 긴 오류문의 첫 줄이 아니라 마지막 줄에 진짜 원인이 적혀 있다

### 어텐션 커널 최적화(FlashAttention 계열)의 아이디어 개관

□ 왜 커널(계산 부품) 이야기를 하는가

- 1주차에서 어텐션은 제곱으로 늘어난다고 배웠다. 그런데 실제 GPU에서 돌려 보면, 수식상의 계산량보다 **데이터를 이리저리 옮기는 일**이 더 큰 병목인 경우가 많다
- 비유: 요리사가 칼질(연산)을 아무리 빨리 해도, 재료를 먼 창고(느리고 큰 메모리, HBM)에서 조리대(빠르고 작은 메모리, SRAM)로 오가는 시간이 더 걸리면 전체 요리는 늦어진다
- FlashAttention(arXiv:2205.14135, NeurIPS 2022)은 바로 이 왕복을 줄인다. 어텐션의 **수식은 그대로 두고**(근사가 아니라 정확한 어텐션) 계산 순서를 GPU 메모리 구조에 맞게 재배열한다

□ 핵심 아이디어 두 가지

- 타일링(tiling): 재료를 한꺼번에 다 꺼내지 않고 **한 번에 쓸 만큼만** 조리대에 올린다. 어텐션도 Q, K, V를 작은 조각으로 나눠 칩 안의 빠른 메모리에서 처리하니 창고 왕복이 줄어든다
- 재계산(recomputation): 요리 중간 재료를 전부 창고에 보관해 두지 않고, 필요할 때 **다시 만든다**. 어텐션도 거대한 중간 행렬(n x n)을 저장해 두지 않고 역전파 때 재계산한다. 타일링으로 표를 통째로 만들지 않는 것과 함께, 메모리가 시퀀스 길이에 비례해서만 늘게 된다
- 후속작 FlashAttention-2(arXiv:2307.08691)는 GPU 안에서의 일 분배를 다듬어 같은 하드웨어에서 처리량을 더 끌어올렸다

<img src={gpuMemory.src} alt="GPU 칩 안의 연산 코어와 작고 빠른 SRAM 조리대, 칩 밖의 크고 느린 HBM 창고 사이의 느린 왕복, 그리고 n 곱하기 n 어텐션 표를 작은 조각으로 나누는 타일링을 보여주는 구조도" style="max-width: 100%; border-radius: 8px; margin: 1rem 0;" />

○ 타일링을 4 x 4 표로 따라가기

- 1주차의 4토큰 점수표(4 x 4 = 16칸)를 다시 꺼내자. 일반 계산은 16칸 전체를 한꺼번에 창고에서 조리대로 옮겨 계산하고, 결과를 다시 창고로 보낸다
- 타일링은 표를 **2 x 2 조각 4개**로 나눈다. 조리대에는 한 번에 4칸만 올린다. 조각 1을 계산해 결과를 정리하고, 조각 2, 3, 4를 차례로 처리한다
- 조리대(빠른 메모리)는 작아도 괜찮아진다. 한 번에 필요한 공간이 16칸에서 4칸으로 줄었기 때문이다
- 궁금한 점: softmax는 가로줄 전체의 합이 1이 되게 하는 계산인데, 조각으로 나눠도 되나? 조각을 하나 처리할 때마다 지금까지의 합계 정보를 넘겨받아 앞의 결과를 고쳐 나가기 때문에, 최종 결과는 한꺼번에 계산한 것과 같다

<img src={tilingBlocks.src} alt="왼쪽은 4 곱하기 4 표 16칸 전체를 한꺼번에 옮기는 일반 계산, 오른쪽은 같은 표를 2 곱하기 2 조각 네 개에 1부터 4까지 번호를 붙여 나눠 처리하는 타일링" style="max-width: 100%; border-radius: 8px; margin: 1rem 0;" />

- 실제 크기로 옮겨 보자. 토큰 4,096개의 점수표 한 장은 16,777,216칸, 64MiB다. 설명용으로 조각을 256 x 256으로 자르면 조각 하나는 65,536칸, 65,536 x 4바이트 = **0.25MiB**다. 조각 수는 (4,096 / 256) x (4,096 / 256) = 16 x 16 = **256개**다
- 64MiB짜리 표를 한 번에 옮기는 대신 0.25MiB 조각을 조리대 안에서 차례로 처리한다. 실제 조각 크기는 GPU의 빠른 메모리 크기에 맞춰 정해진다

○ 재계산이 아끼는 양

- 1주차에서 12층, 층마다 12헤드 모델에 토큰 4,096개를 넣으면 점수표 144장, **약 9GiB**가 필요하다고 계산했다
- 역전파(2주차 온라인에서 본 거꾸로 따라가기)를 하려면 원래 이 표들을 저장해 둬야 한다. 재계산은 표를 버리고, 출력과 표를 되살리는 데 필요한 작은 값만 남긴다. 역전파 때 조각 단위로 표를 **다시 계산**한다
- 계산을 한 번 더 하는 손해가 있지만, 창고 왕복이 줄어서 전체 시간은 오히려 빨라질 수 있다는 것이 FlashAttention의 요점이다. 그리고 결과는 근사가 아니라 **원래 어텐션과 같은 계산**이다

□ 우리 수업과의 연결

- "같은 모델인데 왜 이 환경에서는 느린가"의 답 절반은 수식이 아니라 **커널과 메모리**에 있다
- 우리가 커널을 직접 짤 일은 없다. **라이브러리가 이미 만들어 둔 최적화를 알고 선택하는 것**이 실무 역량이다. 도내 소규모 조직처럼 장비가 부족한 조건일수록 이 선택이 비용을 가른다

### 최신 사례 - DeepSeek-V4.1-Flash의 어텐션 효율화

□ 왜 이 사례를 보는가

- FlashAttention은 **같은 계산을 더 빠르게** 하는 방법이었다. 2026년 9월에 공개된 DeepSeek-V4.1-Flash는 한 걸음 더 나가서, 어텐션이 **무엇을 기억하고, 누구와 나눠 쓰고, 얼마나 촘촘히 적을지**를 크게 다시 설계했다
- 이 절의 내용은 공개된 기술 보고서("DeepSeek-V4.1-Flash: Pushing the Limits of KV Cache Compression")와 함께 공개된 모델 설정 파일(config.json)에서 가져왔다. 보고서에 없는 숫자는 설정 값으로 **직접 계산한 것**이며, 그때마다 계산 과정을 보인다
- 결과부터 보자. 보고서가 밝힌 핵심 숫자는 다음과 같다

□ 준비 - 두 종류의 어텐션과 두 곳의 저장소

- 이 모델의 층은 대부분 어텐션을 두 갈래로 함께 쓴다
- **슬라이딩 윈도 어텐션**(SWA): 바로 앞 **128개 토큰**만 보는 창문이다. 창문 크기가 고정이라 문맥이 아무리 길어져도 메모리가 늘지 않는다
- **전역 어텐션**: 문맥 전체에서 필요한 것을 찾아본다. 1주차에서 본 KV 캐시(앞 토큰들의 Key·Value 메모장)가 여기서 생긴다
- 메모장을 두는 곳도 두 군데다. 지금 계산 중인 것은 GPU에 붙은 HBM(이번 주의 "창고". 칩 안 SRAM보다는 느리지만 SSD보다는 훨씬 빠르다)에, 다음에 같은 앞부분이 들어오면 재사용하려는 것은 SSD나 서버 메모리에 **오래 보관**한다
- 어느 쪽이 큰지 보자. 전역 KV는 토큰당 890바이트라서 문맥이 길수록 정비례로 커진다. 100만 토큰이면 890 x 1,000,000 = 약 **849MiB**다. 반면 SWA KV는 층마다 창문 128칸만 들고 있어 문맥 길이와 상관없이 크기가 고정이다. 그래서 보고서도 "문맥이 충분히 길면 전역 KV가 KV 메모리의 대부분을 차지한다"고 설명한다. 긴 문맥에서 줄여야 할 것은 **전역 KV**다

□ 기법 1 - CSA2: 압축하고, 골라 읽고, 층끼리 나눠 쓴다

- CSA2(Compressed Sparse Attention 2)는 KV 캐시 비용을 **세 방향**에서 동시에 줄인다. 보고서가 정리한 세 방향은 다음과 같다
- 항목 크기 줄이기: KV 한 칸에 담는 숫자 묶음을 작게 한다. 이 모델의 main KV는 512채널짜리 묶음 **하나**를 모든 헤드가 함께 쓴다
- 시퀀스 방향 줄이기: 토큰 여러 개를 KV 항목 하나로 **압축**한다. 인코더의 CSA2 층은 압축 비율이 2라서 토큰 2개가 항목 1개가 된다. 1주차의 "요약본" 아이디어를 조금 섞은 셈이다
- 층 방향 줄이기: 층마다 따로 메모장을 만들지 않고 **앞 층의 메모장을 빌려 쓴다**. 이전 연구에도 있던 아이디어지만, CSA2는 세 방향을 한꺼번에 쓰고 메모장 공유와 선택 재사용을 따로 켤 수 있게 했다

○ 골라 읽기 - 인덱서와 Top-512

- 전역 KV 항목이 수십만 개여도 각 쿼리는 전부 읽지 않는다. 가벼운 **인덱서**(색인기)가 모든 항목에 점수를 매기고 점수가 높은 **512개**만 고른다
- 인덱서는 도서관의 목록 카드와 같다. 내 검색어(Indexer Q)와 카드(Indexer K)를 비교해 읽을 책 512권을 추리고, 실제 책 내용(main KV)은 그 512권만 펼친다
- 각 쿼리가 실제로 읽는 것은 고른 512개와 최근 SWA 128개를 합한 **640개**다. 100만 토큰 문맥이라면 전부 읽을 때의 1,000,000 / 640 = 약 **1,560분의 1**이다
- 보고서에 따르면 이 희소 어텐션은 처음부터(길이 64K에서) 희소한 상태로 학습했고, 모든 토큰을 보는 어텐션으로 먼저 익히는 단계를 거치지 않았다

○ 나눠 쓰기 - 세 가지 모드

- CSA2 층은 학습 전에 정해 둔 세 모드 중 하나로 동작한다. 모든 모드에서 **자기 질문(Main Q)과 SWA KV는 직접 계산**하고, 나머지를 얼마나 빌리느냐가 다르다

<img src={dsCsa2Modes.src} alt="Full, Reindex, Reuse 세 모드가 Main Q, SWA KV, Main KV, Indexer K, Indexer Q, Top-K 목록을 각각 직접 계산하는지, 앞 Full 층 것을 빌리는지, 앞 층의 선택을 빌리는지, 쓰지 않는지를 색으로 구분한 표" style="max-width: 100%; border-radius: 8px; margin: 1rem 0;" />

- **Full 모드**: 전역 KV와 목록 카드를 직접 만들고, 직접 검색해 512개를 고른다. 모든 일을 스스로 하는 층이다
- **Reindex 모드**: 전역 KV와 목록 카드는 앞의 Full 층 것을 빌린다. 대신 **자기 검색어로 다시 검색**해서 자기만의 512개를 고른다. 같은 책장을 쓰되 층마다 필요한 책이 다를 수 있기 때문이다
- **Reuse 모드**: 전역 KV도, 고른 512개 목록도 앞 층 것을 **그대로** 쓴다. 검색을 아예 하지 않으니 가장 가볍다
- 비유로 정리하면, Full은 필기를 직접 하는 학생, Reindex는 친구 필기를 빌려서 형광펜만 자기가 긋는 학생, Reuse는 친구가 형광펜까지 그어 둔 필기를 그대로 보는 학생이다

○ 890바이트를 손으로 맞춰 보기

- main KV 항목 하나: 보고서는 512채널짜리 main KV를 4비트(E2M1)로 적고 16채널마다 8비트 보조 눈금(E4M3)을 하나씩 붙인다고 밝혔다. 512 x 0.5 = 256바이트, 보조 눈금 512 / 16 = 32바이트. 합계 **288바이트**
- 인코더 Full 층 3개: 압축 비율 2라 토큰 하나당 항목 0.5개. 288 x 0.5 x 3 = **432바이트**
- 디코더 Full 층 1개: 압축 없음. **288바이트**
- main KV 합계는 432 + 288 = **720바이트**다. 890바이트에서 남는 **170바이트**는 목록 카드(Indexer K) 등의 몫이다. 보고서가 목록 카드의 저장 형식을 자세히 밝히지 않아서, 이 부분은 뺄셈으로만 구하고 더 쪼개지 않는다

□ 기법 2 - 계층형 희소 인덱서: 1차 서류 심사로 후보를 추린다

- 골라 읽기 덕분에 어텐션은 가벼워졌지만, **고르는 일**(인덱서 채점)은 여전히 문맥 전체를 훑는다. 100만 토큰이면 검색할 때마다 100만 개에 점수를 매겨야 한다
- 디코더에서는 이 문제를 **1차 심사와 면접**처럼 푼다
- 1차 심사: 디코더의 첫 Full 층(20층)이 문맥 전체에 점수를 매긴다. 자기 Top-512를 고르는 동시에, 위치 8개씩 묶은 **블록**마다 안에 든 위치 중 최고 점수를 블록 점수로 삼고, 점수가 가장 높은 블록을 최대 **2,048개** 뽑는다. 이 블록들이 덮는 위치, 최대 2,048 x 8 = **16,384개**가 후보 풀이다
- 면접: 뒤의 Reindex 층(24, 28, 32, 36층)은 전체가 아니라 **후보 풀 16,384개 안에서만** 다시 채점해 각자 512개를 고른다

<img src={dsIndexerFunnel.src} alt="100만 토큰 문맥에서 첫 Full 층이 전체 1,000,000개 위치를 훑고, 블록 2,048개 곱하기 8칸의 후보 풀 16,384개로 줄인 뒤, 층마다 Top-512를 고르고, 실제로는 SWA 128개를 더해 640개 항목을 읽는 과정을 로그 눈금 막대로 보여주는 그림" style="max-width: 100%; border-radius: 8px; margin: 1rem 0;" />

- 효과: 뒤 층의 채점 대상이 **문맥 길이와 상관없이 최대 16,384개로 제한**된다. 100만 토큰이면 1,000,000 / 16,384 = 약 **61분의 1**이다. 문맥이 25만 토큰이든 100만 토큰이든 뒤 층의 채점 수는 최대 16,384개로 같다
- 대신 첫 Full 층은 여전히 전체를 한 번 훑는다. 그리고 이 제한은 사후 학습 단계에서 **학습 때도 똑같이** 적용해서, 뒤 층 인덱서가 "후보 풀 안에서만 고르는" 상황에 익숙해지도록 했다

□ 기법 3 - FP4 KV 캐시: 메모장을 작은 글씨로

- 3주차에서 자세히 배울 **양자화**를 미리 맛본다. 숫자를 적는 비트 수를 줄이면 저장 공간이 준다
- 이 모델은 main KV를 **4비트**(E2M1 형식)로 저장한다. 4비트로 적을 수 있는 값은 0, 0.5, 1, 1.5, 2, 3, 4, 6과 그 음수, 모두 **15가지뿐**이다. 그래서 채널 16개마다 **보조 눈금**(스케일, 8비트 E4M3 형식) 하나를 붙여 "이 묶음은 몇 배로 읽어라"를 함께 적는다

○ 숫자 4개로 따라 하기 (설명용 예시)

- 저장할 값이 [0.8, -2.3, 5.1, 0.1]이라고 하자
- 1단계, 보조 눈금 정하기: 절댓값이 가장 큰 5.1이 눈금의 끝인 6에 오도록 5.1 / 6 = **0.85**로 정한다 (실제로는 보조 눈금도 8비트라 0.875 같은 가까운 값으로 맞추지만, 계산을 쉽게 하려고 0.85를 쓴다)
- 2단계, 나누기: 0.8 / 0.85 = 0.94, -2.3 / 0.85 = -2.71, 5.1 / 0.85 = 6.00, 0.1 / 0.85 = 0.12
- 3단계, 가장 가까운 눈금에 맞추기: 0.94 → **1**, -2.71 → **-3**, 6.00 → **6**, 0.12 → **0**
- 4단계, 되살리기: 1 x 0.85 = 0.85, -3 x 0.85 = -2.55, 6 x 0.85 = 5.1, 0 x 0.85 = 0. 원래 값 [0.8, -2.3, 5.1, 0.1]과 조금씩 다르다. 이 차이가 **정밀도 손실**이다

<img src={dsFp4Grid.src} alt="FP4 E2M1 형식이 표현할 수 있는 15개 눈금 값을 수직선에 찍고, 예시 값 0.8, -2.3, 5.1, 0.1을 스케일 0.85로 나눈 0.94, -2.71, 6.00, 0.12가 각각 가장 가까운 눈금 1, -3, 6, 0으로 맞춰지는 모습을 화살표로 보여주는 그림" style="max-width: 100%; border-radius: 8px; margin: 1rem 0;" />

○ 보고서가 밝힌 주의점

- 손실을 줄이려고 **학습 중에 4비트 저장을 흉내 내는 방식**(QAT, 양자화 인식 학습)으로 사후 학습했다. 모델이 거친 눈금에 미리 적응하게 하는 것이다
- 이전 세대의 8비트(FP8) main KV와 비교해 저장 공간이 **거의 절반**이 됐다
- 표현할 수 있는 가장 큰 값은 보조 눈금 최대 448 x 6 = **2,688**이다. 이 모델의 KV 값은 이론상 최대 약 22.6, 학습 중 실제로는 약 10이라서 여유가 충분하다
- 모든 것을 4비트로 바꾸지는 않았다. **SWA KV는 양자화에 민감해서 8비트를 유지**했다. 줄일 곳과 지킬 곳을 나눈 것이다

□ 기법 4 - 인과 인코더-디코더와 SWA 제한 재생: 위층은 처음부터 다시 읽지 않는다

- 에이전트는 도구를 부를 때마다 긴 입력을 새로 처리(prefill)한다. 메모장을 재사용하지 못하면 매번 긴 입력 전체를 40개 층에 통과시켜야 한다
- **인과 인코더-디코더**(CED): 아래 20층을 인코더, 위 20층을 디코더로 나눈다. 디코더의 전역 KV는 디코더 층을 계산해서 얻지 않는다. 디코더의 Full 층(20번 층)이 **인코더 마지막 층(19번 층)의 출력에서 바로 뽑아내고**(투영), 나머지 디코더 층은 기법 1에서 본 대로 그것을 빌려 쓴다

<img src={dsCed.src} alt="긴 입력 전체가 인코더 20개 층을 통과해 인코더 마지막 층 출력이 되고, 거기서 디코더 Full 층이 전역 KV를 바로 투영하며, 끝부분 128토큰만 디코더 SWA 재생을 거쳐 답 생성을 시작하는 흐름도" style="max-width: 100%; border-radius: 8px; margin: 1rem 0;" />

- 계산으로 확인해 보자. 입력 100,000토큰, 층 40개, 창문 128이라고 하면 기존 방식의 "층 x 토큰" 계산은 100,000 x 40 = **4,000,000**이다
- CED는 입력 전체가 인코더 20층만 지나고(100,000 x 20 = 2,000,000), 디코더는 끝부분 128토큰만 지난다(128 x 20 = 2,560). 합계 **2,002,560**, 기존의 **절반**(약 50%)이다. 보고서도 입력 처리 계산이 거의 절반으로 준다고 밝혔다

○ 왜 끝부분 128토큰만 다시 읽어도 되나 - SWA 제한 재생

- 문제는 SWA다. SWA는 층마다 자기 계산이 필요해서, 정확히 복원하려면 층이 쌓인 만큼 더 앞까지 봐야 한다. 창문 128칸이 층마다 겹겹이 이어지기 때문이다
- 정확한 복원: 40층 전체라면 40 x 128 = **5,120토큰**을 다시 계산해야 한다 (디코더만이면 20 x 128 = 2,560토큰)
- **제한 재생**(Bounded Replay): 마지막 **128토큰만** 다시 계산하고, 그보다 앞은 없는 셈 친다. 결과는 정확한 값이 아니라 **근사**지만, 보고서의 실험에서는 답변 품질 저하가 거의 없었다. 디코더 쪽 재생은 안전을 위해 사후 학습 때도 흉내 냈다
- 이 근사 덕분에 저장 전략도 바뀌었다. 이전 세대에서는 오래 보관하는 캐시의 **거의 절반이 SWA KV**였다. 이제 인코더 SWA KV는 SSD에 보관하지 않고 서버 메모리의 10%를 쓰는 공간에 **몇 분만** 두며, 사라지면 128토큰만 다시 계산한다. 디코더 SWA KV는 아예 보관하지 않고 매번 재생으로 만든다. 전역 KV는 **72시간 이상** 보관한다
- 그래서 오래 보관하는 캐시가 약 1/8이 됐다. SWA KV를 빼서 **거의 절반**, 남은 전역 KV가 **1/4**이므로 1/2 x 1/4 = **1/8**이다

□ 한 장으로 정리

| 기법 | 줄이는 것 | 핵심 아이디어 | 대가 또는 주의 |
|---|---|---|---|
| 압축 + Top-512 선택 | 어텐션이 읽는 양 | (인코더) 토큰 2개를 항목 1개로, 512개 + 최근 128개만 읽기 | 인덱서가 잘 골라야 한다 |
| CSA2 층 간 공유 | 전역 KV 저장 | 40개 층 중 4개 층만 메모장을 만든다 | 공유 구조로 학습해야 하고, 분산 학습에 추가 장치가 든다 |
| 계층형 희소 인덱서 | 인덱서 채점 | 뒤 층은 최대 16,384개 후보 풀 안에서만 | 첫 Full 층은 여전히 전체를 훑는다 |
| FP4 main KV | 항목 하나의 크기 | 4비트 + 16채널당 보조 눈금 | 정밀도 손실, QAT 필요, SWA KV는 8비트 유지 |
| 인과 인코더-디코더 | 입력 처리 계산 | 디코더 전역 KV를 인코더 출력에서 투영 | 디코더 SWA를 재생해야 한다 |
| SWA 제한 재생 | 재계산과 장기 저장 | 128토큰만 다시 계산 | 결과가 근사다 |

- 이 기법들과 다른 구조 개선(mHC, Engram, DSpark 등)이 모두 합쳐져서, 문맥을 4K에서 1M으로 256배 늘려도 토큰 하나를 만드는 계산량은 **약 1/4만** 늘어난다고 보고서는 밝혔다 (8비트·4비트 계산을 가볍게 치는 가중치를 적용한 수치)

□ FlashAttention과 무엇이 다른가

- **FlashAttention**: 수식은 그대로, 계산 순서와 메모리 사용만 바꿨다. 결과는 원래 어텐션과 **같다**
- **DeepSeek-V4.1-Flash**: 무엇을 읽을지(512개 선택), 누가 기억할지(층 간 공유), 얼마나 촘촘히 적을지(4비트), 얼마나 다시 계산할지(128토큰 재생)를 바꿨다. 일부 결과가 **근사**가 되는 대신 비용을 크게 줄였다
- 그래서 판단 기준이 달라진다. "정확한가"만이 아니라 "**근사로 잃는 품질이 아낀 비용에 비해 작은가**"를 물어야 한다. 보고서는 품질 저하가 미미하다고 밝혔지만, 이는 개발사 자체 평가다. 우리 과제에 쓸 때는 직접 확인한다. 긴 문맥 추론은 7주차에서 더 깊이 다룬다

| 그래디언트 | 가중치를 조금 바꿀 때 손실이 얼마나, 어느 쪽으로 변하는지 |

| 학습률 (lr) | 한 걸음의 크기 |
| MSE / MAE | 오차를 제곱해 평균 / 절댓값으로 평균 낸 손실 |
| 배치 / step / 에폭 | 한 번에 넣는 묶음 / 묶음 하나 처리 / 데이터 전체 한 바퀴 |

| 체크포인트 | 미리 학습해 저장해 둔 가중치 파일 |

| SRAM / HBM | GPU의 작고 빠른 메모리 / 크고 느린 메모리 |
